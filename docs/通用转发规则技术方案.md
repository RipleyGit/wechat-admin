# 通用转发规则技术方案

## 1. 背景与目标

服务号的回调地址只能配置一个，所有事件都先到 wechat-admin。部分事件（例如 pco 商户绑定二维码的扫码和关注）需要由其他后端处理。

目标是在自动回复模块中增加一种「转发」规则：命中规则的事件，wechat-admin 把微信原始 XML 原样发送到规则中配置的地址。转发与本地的关注、扫码、取消关注处理并行执行。转发的目标地址由规则配置决定，代码中不写死任何业务域名。

示例：规则「pco 商户绑定」，匹配 `pco_bind_merchant_`（右模糊），事件类型为 SCAN 和 subscribe，目标地址为 `https://pco.bleem.site/api/wechat-event/event`。

## 2. 已确认的决策

1. 接受 wechat-admin 作为通用转发器，主动请求规则配置的外部地址。这是对 `CLAUDE.md` 中「两个后端不互相调用」约定的例外，由项目负责人确认。
2. 命中转发规则后，转发与本地的 `SubscribeHandler`、`ScanHandler`、`UnsubscribeHandler` 并行执行。本地的关注状态更新和自动回复照常进行，转发不跳过本地处理。
3. 取消关注也支持转发。取消关注没有场景值，规则按事件类型 `unsubscribe` 匹配，匹配内容留空。

## 3. 术语

- **右模糊匹配**：事件场景值以规则关键词开头，即 `startsWith`。例如规则 `pco_bind_merchant_` 命中 `pco_bind_merchant_tenantA_123_1783000000`。
- **场景值**：SCAN 事件的 EventKey 原样是场景值；subscribe 事件的 EventKey 带 `qrscene_` 前缀，匹配前需去掉该前缀。

## 4. 现状（已核实代码）

- `WxMpPortalController`（`modules/wx/controller/`）接收 `/wx/msg/{appid}` 的 POST，校验签名后解析为 `WxMpXmlMessage`，交给 `WxMpMessageRouter`。原始请求体只存在于局部变量 `requestBody` 中，处理器拿不到。
- `WxMpMessageRouterConfiguration` 中，EVENT 类型的 SUBSCRIBE 和 SCAN 分别由 `SubscribeHandler` 和 `ScanHandler` 处理。二者最终调用 `MsgReplyService.tryAutoReply`。
- `MsgReplyRuleServiceImpl.getMatchedRules` 只支持精确匹配（`equals`）和包含匹配（`contains`），并过滤生效时段和 appid。
- `MsgReplyRule` 实体的 `replyType` 是字符串，已有的类型包括文本、图片、语音、视频、音乐、图文、小程序、菜单等。没有转发类型。
- 已有规则不区分事件类型，任何消息都可能命中。

## 5. 数据模型变更

表 `wx_msg_reply_rule` 新增两个字段，migration 文件为 `api/db/migrations/20261029_wx_msg_reply_rule_forward.sql`，写成可重复执行。

| 字段 | 类型 | 说明 |
|------|------|------|
| `match_mode` | varchar(16) NULL | `exact` / `contains` / `prefix`。为 NULL 时沿用 `exact_match`：为 true 按精确，否则按包含。历史规则不回填 |
| `event_type` | varchar(16) NULL | `SCAN` / `subscribe` / `unsubscribe`。NULL 表示不限，但只匹配带场景值的关注和扫码，不匹配取消关注。取消关注必须显式选 `unsubscribe`，此时匹配内容留空。仅对转发规则生效 |

`replyType` 新增取值 `forward`，`replyContent` 存目标 URL。

已有规则的 `exact_match` 字段保留，其含义和行为不变。

## 6. 匹配与处理流程

```
微信 POST /wx/msg/{appid}
  -> 校验签名
  -> 保存原始 requestBody 到请求上下文（ThreadLocal 或作为参数传入）
  -> 解析 WxMpXmlMessage
  -> 若 MsgType=event 且 Event 为 SCAN、subscribe 或 unsubscribe：
       -> 取场景值（subscribe 去掉 qrscene_ 前缀；unsubscribe 没有场景值，跳过此步）
       -> 查询 replyType=forward、状态启用、生效时段内、appid 匹配的规则
       -> 按 event_type 与 match_mode 过滤（unsubscribe 只按 event_type 匹配）
       -> 若有命中：
            异步对每条命中规则发起转发，路由继续（next），不结束
  -> 本地的 SubscribeHandler / ScanHandler / UnsubscribeHandler 照常执行
  -> 返回本地 handler 的响应（微信不展示回复）
```

路由中，转发规则的匹配器注册在 SUBSCRIBE、SCAN、UNSUBSCRIBE 规则之前，并以 `next()` 结束注册。命中时执行转发，然后继续匹配后续的本地规则。

`getMatchedRules` 查询普通自动回复时必须排除 `replyType=forward` 的规则，否则目标 URL 会被当作文本发给用户。

## 7. 转发请求

- 方法：POST
- 地址：规则的 `replyContent`
- Content-Type：与微信原始请求一致，`text/xml`
- 请求体：微信原始 XML，原样发送，不修改任何字段（尤其是 `FromUserName` 和 `EventKey`）
- 超时：连接和读取各 3 秒，留出余量给微信 5 秒限制。转发在异步任务中执行，不影响对微信的响应
- 响应：记录目标返回的 HTTP 状态码和响应体，不把目标响应返回给微信。wechat-admin 对微信始终返回空响应

转发失败（超时、连接错误、非 2xx）时，记录错误日志，包含 `openid`、`EventKey`、规则 ID 和目标地址。v1 不做自动重试，避免重复绑定。

## 8. 安全

目标地址由管理员配置，服务端会主动发起请求，需防止 SSRF：

- 只允许 `https` 协议
- 解析域名后拒绝内网、回环（127.0.0.0/8、::1）、链路本地（169.254.0.0/16）和私有网段（10/8、172.16/12、192.168/16）地址
- 保存规则时校验 URL 格式，运行时再次校验解析后的 IP，防止 DNS 重绑定
- 转发接口的管理权限码（`wx:msgreply:*` 等）必须在 migration 中种进 `sys_menu`

通用转发不设域名白名单，允许配置任意公网 https 地址。这意味着拥有规则管理权限的人可以把用户事件推送给任何外部服务，需要在权限分配上控制。

## 9. 管理界面

规则表单（`web/`）增加：

- 回复类型选项「转发」，选中后回复内容填目标 URL
- 匹配方式下拉：精确、包含、右模糊
- 事件类型下拉：不限、SCAN、subscribe、unsubscribe。选 unsubscribe 时隐藏匹配内容和匹配方式

## 10. 测试计划

本地用 Colima 容器跑实例验证（参考 `local-test-harness.md`），不在生产服务器上启动 JVM。

- 单元测试：场景值解析（含 `qrscene_` 前缀）、三种匹配模式、事件类型过滤、URL 校验（拒绝 http、内网地址）
- 集成测试：用本地 HTTP 服务模拟目标地址，验证请求体与原始 XML 字节一致
- 回归：无转发规则时，SUBSCRIBE 和 SCAN 的本地处理与原来一致；普通自动回复规则不受影响
- 使用 `mvn compile` 在 JDK 8 下编译，前端执行 `npm run build`

## 11. 已知影响与待确认

1. **转发与本地处理互不等待**：转发失败或超时，不影响本地的关注状态更新、取消关注状态更新和自动回复。接收方收到的事件与本地处理的结果是各自独立的。
2. **多条命中规则**：v1 对所有命中的转发规则各发送一次请求，不按优先级截断。

## 12. 范围之外

- 文本消息的转发（v1 只处理 SCAN 和 subscribe 事件）
- 失败自动重试和死信队列
- 转发日志的界面查询（v1 只写应用日志）
