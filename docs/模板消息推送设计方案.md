# 通用消息推送机制设计（模板消息优先）

## 1. 背景与定位

现有 `/wx/notify/{code}` 是**通道驱动**的：调用方只传变量，通道里预置了收件人、模板和文案，适合部署通知这类固定场景。

新需求是**调用方驱动**：模板 ID、消息内容、收件人全部由请求决定，适合业务系统按事件实时推送。两者定位不同，新接口与现有通道并存，不替换 `/wx/notify/{code}`。

本文聚焦模板消息；客服消息只预留字段和扩展点。

## 2. 接口设计

### 2.1 路径与鉴权

```http
POST /wx/push/template
X-Notify-Secret: <公众号推送密钥，48 位十六进制>
```

- 复用 `wx_account.notify_secret` 做鉴权，与现有网关一致
- 路径放在 `/wx/**` 下（Shiro 匿名），不走 `/manage/**` 登录态
- 新开 `PushGatewayController`，不复用 `/notify/{code}`，避免通道 code 与固定路径冲突

### 2.2 请求体

```json
{
  "templateId": "9bRz...",
  "data": [
    { "name": "first",    "value": "您有一条新工单" },
    { "name": "keyword1", "value": "A-20261113-001" },
    { "name": "keyword2", "value": "2026-11-13 10:00" },
    { "name": "remark",   "value": "请及时处理" }
  ],
  "url": "https://example.com/detail/1",
  "miniprogram": {
    "appId": "wx62c3973df7065a2b",
    "pagePath": "pages/launch/launch?app=pco"
  },
  "targets": {
    "openids":   ["oXXXX"],
    "phones":    ["13800000000"],
    "nicknames": ["张三"],
    "tagids":    [101, 102]
  },
  "clientMsgId": "order-123-push-1",
  "sendType": "template"
}
```

字段说明：

| 字段 | 必填 | 说明 |
|------|------|------|
| `templateId` | 是 | 公众号模板 ID |
| `data` | 是 | 按微信官方格式，`name` 必须覆盖模板里的全部 `{{xxx.DATA}}` |
| `url` | 否 | 点击跳转 H5；与 `miniprogram` 同时存在时，新版本微信优先打开小程序 |
| `miniprogram` | 否 | 跳转小程序，字段为 `appId` / `pagePath`（驼峰，Jackson 不认 Gson 的 `@SerializedName`） |
| `targets` | 是 | 四个数组**至少要有一个非空**；传多个时取并集去重 |
| `clientMsgId` | 否 | 调用方幂等键，重复请求返回首次结果 |
| `sendType` | 否 | 默认 `template`；预留 `kefu`（当前实现忽略该字段，一律按模板消息发送） |

`targets` 的 `openids` / `phones` / `nicknames` / `tagids` 四个数组全为空或都不传 → 400「至少指定一个推送目标」。各数组最多 100 个元素，解析去重后的收件人总数也不能超过 100。超过直接拒绝，让调用方分批。

### 2.3 响应

全部成功或部分成功都返回 `code=200`，用计数字段表达结果：

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "batchId": "b_20261113_xxx",
    "requested": 6,
    "resolved": 5,
    "duplicate": 1,
    "successCount": 4,
    "failCount": 1,
    "failures": [
      { "openid": "oYYYY", "reason": "system error" }
    ]
  }
}
```

- `requested`：请求里各数组元素总数
- `resolved`：解析并去重后的 openid 数
- `duplicate`：被去重掉的数量
- `failures` 只来自**发送阶段**的单条失败（微信返回错误、网络异常），最多返回前 50 条，完整记录落库
- 校验类错误走 4xx，响应里没有 `failures`，错误清单放在 `msg` 里

### 2.4 错误码

所有**校验类**错误都在发送前抛出，保证 4xx 时一条消息都没发：

| code | 场景 |
|------|------|
| 401 | 推送密钥无效 |
| 400 | 模板不存在（本地和微信都没有） |
| 400 | 模板字段缺失：`data` 未覆盖模板全部关键字 |
| 400 | openid 不在该公众号粉丝中 |
| 400 | 手机号无法解析到唯一粉丝 |
| 400 | 昵称不存在 |
| 400 | 解析出的收件人中有已取关用户（整批失败，返回取关清单） |
| 400 | tagid 不存在 |
| 400 | `targets` 四个数组全为空 / 收件人超过单次上限 |

错误信息要**聚合**，不要遇到第一个就返回：

```text
以下 openid 不在公众号粉丝中：o1, o2
以下手机号无法解析到粉丝：13800000000
以下昵称查不到粉丝：张三
以下用户已取关，无法推送：o3, o4
```

实现注意：`RRException` 的默认 `code` 是 **500**，校验类错误必须显式传 400
（`new RRException(msg, 400)`），否则对接方收到的是 500，会被当成可重试错误。

对外文档见 [模板消息推送接口对接文档.md](模板消息推送接口对接文档.md)，两边错误码要同步改。

## 3. 模板解析

调用方传 `templateId`，按以下顺序解析：

1. 查本地 `wx_msg_template`：`appid = ? AND template_id = ? AND status = 1`
2. 本地没有，调微信 `wxMpService.getTemplateMsgService().getAllPrivateTemplate()` 拉取该公众号全部模板
3. 在返回列表里按 `template_id` 匹配：
   - 命中：upsert 到 `wx_msg_template`（按 `appid + template_id`），然后使用
   - 未命中：返回 400「模板不存在或尚未添加到该公众号」
4. 拉取结果建议在 Redis 缓存 10 分钟，避免调用方传错 ID 时每次都打微信接口

**注意**：只能拉取**该公众号已经添加过**的模板。任意 templateId 不会凭空变出来；新增模板仍需在微信后台模板库添加，或后续做一个管理端「从模板库添加」的功能（`addTemplate(shortTemplateId)`）。

模板字段校验：

- 从 `wx_msg_template.content` 里提取所有 `{{keyword1.DATA}}` 形式的字段名
- 要求请求 `data` 覆盖全部字段名，缺哪个报哪个
- 请求里多出来的字段忽略并记日志，不阻断
- 值长度由微信按字段类型校验（`thing` 20 字符等），我们只做非空和类型转字符串，不重复实现微信规则

## 4. 收件人解析

四种收件人先分别解析成 openid，再合并去重。所有解析都在发送前完成。

### 4.1 openid

```sql
SELECT openid, subscribe FROM wx_user
WHERE appid = ? AND openid IN (...)
```

- 有 openid 不在结果里 → 400，列出全部缺失项
- `subscribe = 0` → **整批失败**，返回全部已取关的 openid，一条消息都不发。这是明确的产品决策：宁可整批不发，也不做部分送达

### 4.2 手机号

只查 `wx_user`，不跨到 `wx_mini_user`：

```sql
SELECT openid, subscribe FROM wx_user
WHERE appid = ? AND phone IN (...)
```

- 查不到的手机号 → 400，列出全部缺失项
- 一个手机号命中多个 openid → 400「手机号 138... 对应多个粉丝，无法确定收件人」，不要猜
- 命中但 `subscribe = 0` → 整批失败，返回取关清单

**注意**：`wx_user.phone` 在本仓库没有可靠的写入路径（`refreshUserInfo` 从微信拿不到手机号），这条推送能否用，取决于库里这一列是否被其他流程回填过。上线前建议先查目标公众号的 `phone` 非空率；如果基本为空，手机号推送暂时只能算预留能力。

### 4.3 昵称

```sql
SELECT openid, subscribe FROM wx_user
WHERE appid = ? AND nickname IN (...)
```

- 昵称不唯一：**命中几个就发给几个**，合并去重后计入 `resolved`，响应里体现去重数量
- 某个昵称完全查不到 → 400，列出缺失昵称
- 命中的用户里有 `subscribe = 0` → 整批失败，返回取关清单
- 昵称可能为空（用户未授权）或随时变更，不适合作为强标识；调用方应优先用 openid

### 4.4 tagid

微信模板消息接口**不支持按标签群发**，标签必须在本地展开成 openid。

1. 校验 tagid 是否存在：`wxUserTagsService.getWxTags(appid)`（已有 10 分钟 Redis 缓存），不存在的 tagid 聚合报 400
2. 本地展开：

   ```sql
   SELECT openid FROM wx_user
   WHERE appid = ? AND subscribe = 1
     AND JSON_CONTAINS(tagid_list, CAST(? AS JSON))
   ```

3. 多个 tagid 取并集，再去重
4. 标签存在但本地没有粉丝命中：不算错误，该标签贡献 0 个收件人；如果最终总数为 0，返回 400「没有解析到任何收件人」
5. tagid 是群体选择，只展开 `subscribe = 1` 的粉丝；已取关的人不参与，也不会让整批失败。否则一个标签下有历史取关用户，标签推送就永远不可用
6. `wx_user.tagid_list` 可能滞后。标签下本地查不到人时，可退化为微信 `tagListUser(tagid, nextOpenid)` 分页拉取，再以微信结果为准

性能提示：`JSON_CONTAINS` 用不上索引，粉丝量大时是逐行扫描。当前 `NotifyServiceImpl.resolveRecipients` 也是这个做法。如果单账号粉丝到十万级，建议后续加 `wx_user_tag(appid, openid, tagid)` 关系表，或直接走微信 `tagListUser`。

### 4.5 组合与去重

- `targets` 至少有一个数组非空；全空直接 400，不发任何消息
- 填了几个来源就解析几个，四种来源的 openid 取**并集**
- 每个来源内部也必须全部命中：任何一个 openid / 手机号 / 昵称 / tagid 在系统里不存在，整批 400，不做部分解析
- 按首次出现顺序去重，保留稳定顺序，便于调用方对照
- 去重后总数超过 100 → 400，让调用方分批
- 全部解析完再发送；任何「不存在」或「已取关」类错误都在发送前抛出

## 5. 发送策略

- 发送前必须 `wxMpService.switchoverTo(appid)`。网关线程没有 ThreadLocal 里的 appid，这是本项目最容易踩的坑
- 逐条调用 `getTemplateMsgService().sendTemplateMsg(msg)`，单条失败不中断其余
- 不复用 `TemplateMsgServiceImpl.sendTemplateMsg`：它是 `@Async` 且不返回结果，新接口需要同步拿结果
- 限速：微信模板消息有按账号的日调用额度，批量发送建议串行 + 小间隔（如 50ms），或按账号维度做令牌桶。不要用无限并发线程池
- 失败重试：v1 不自动重试，避免重复送达；调用方可用 `clientMsgId` 重试，服务端按幂等键返回首次结果
- 幂等：`clientMsgId` 建议在批次表上做 `(appid, client_msg_id)` 唯一索引；重复请求直接返回已存在的批次结果
- 单次上限：解析后超过 100 人直接 400，让调用方分批。后续需要更大量时再引入异步批次

## 6. 日志与审计

### 6.1 批次记录

建议新增 `wx_push_batch`：

| 字段 | 说明 |
|------|------|
| `id` | 自增主键 |
| `batch_id` | 业务批次号（uuid） |
| `appid` | 公众号 |
| `client_msg_id` | 调用方幂等键，可空 |
| `send_type` | `template` / `kefu` |
| `template_id` | 模板 ID |
| `source` | `api` / `manual` |
| `status` | `success` / `partial` / `failed` / `rejected` |
| `client_ip` / `user_agent` | 调用方来源，用于审计 |
| `request_payload` | 原始请求体 JSON |
| `requested_count` / `resolved_count` / `success_count` / `fail_count` | 计数 |
| `error_msg` | 聚合错误 |
| `create_time` / `update_time` | DB 默认值维护 |

### 6.2 逐条记录

复用 `wx_template_msg_log`，补两列：

- `batch_id varchar(64)`：关联批次
- `source varchar(16)`：`api` / `manual`

`send_result` 存微信返回结果或异常摘要。注意 `template_id` 目前是 `varchar(50)`，微信模板 ID 约 43 字符，够用，但建议统一成 `varchar(100)` 与 `wx_msg_template` 一致。

### 6.3 日志脱敏

手机号、昵称属于个人信息。应用日志里手机号打码（`138****0000`），不要把完整请求体打进日志；完整请求体只进数据库，且接口不对外暴露查询。

## 7. 数据模型变更

新增 migration（可重复执行）：

1. `wx_user` 增加索引：
   - `(appid, phone)`
   - `(appid, nickname)`
2. `wx_msg_template`：
   - 新增唯一索引 `(appid, template_id)`
   - 现有 `idx_name` 是**全局唯一**，而 `name` 被写成 templateId；多公众号下建议改成 `(appid, name)`。这是自动拉取模板的前置条件，否则不同公众号插入同名模板会冲突
3. `wx_template_msg_log`：新增 `batch_id`、`source`，索引 `(appid, batch_id)`
4. 新增 `wx_push_batch`
5. `wx_account` 的 `push_enabled` / `push_template_whitelist` **v1 不做**，见 §8

`syncWxTemplate` 目前按 `template_id` 全局删除，不区分 appid；自动拉取模板时不要复用它，改按 `(appid, template_id)` 做定向 upsert。

## 8. 安全

已确认复用 `notify_secret`，不新增密钥。需要明确接受这个风险：这个密钥同时存在 GitHub Actions 里，拿到它就能给该公众号任意粉丝发任意模板消息。

在复用密钥的前提下，保留两项低成本防护：

1. **限流**：Redis 按 `appid + 来源 IP` 计数，例如每分钟 60 次 —— **v1 尚未实现**
2. **审计**：批次表记录来源 IP、User-Agent，保留原始请求体 —— 已实现

模板白名单和 `push_enabled` 开关暂不做，后续如果发现密钥泄露面不可接受再加。

## 9. 客服消息（预留）

请求里的 `sendType` 已预留 `kefu`。后续实现时：

- 复用同一套收件人解析
- 客服消息受 48 小时窗口限制，超窗用户逐条失败，计入 `failures`
- 内容由调用方传 `content`，不需要模板
- 与模板消息共用批次表和逐条日志，`send_type` 区分

## 10. 已确认的决策

| 决策点 | 结论 |
|--------|------|
| 收件人来源 | 四个数组至少填一个；填多个取并集去重；任一目标不存在则整批失败 |
| 手机号来源 | 只查 `wx_user.phone`，不跨 `wx_mini_user` |
| 昵称重名 | 命中多个就全部发送 |
| 已取关用户 | 整批失败，返回取关清单；tagid 展开只取已关注用户 |
| 单次收件人上限 | 100 |
| 鉴权 | 复用 `notify_secret` |
| 管理端页面 | v1 只做接口 + 日志表 |

## 11. 实现拆分

| 部分 | 文件/内容 |
|------|-----------|
| Controller | `PushGatewayController`，`POST /wx/push/template` |
| Service | `TemplatePushService`：模板解析、收件人解析、发送、日志 |
| DTO | `TemplatePushForm`、`TemplatePushResult`、`PushTarget` |
| Mapper | `wx_user` 按 phone/nickname/tag 查询；`wx_msg_template` 按 appid+template_id 查询 |
| Migration | 索引、`wx_push_batch`、`wx_template_msg_log` 补列 |
| 测试 | 收件人解析（缺失/重名/取关）、模板拉取、部分失败、幂等 |

接口是机器对机器，不需要前端。若做管理端记录页，权限码需同步种进 `sys_menu`。
